# Use user-managed authenticated sessions

For a configured target with `authentication.mode: user-session`, require the host capability `browser.user-session/v1`. Never request or accept login credentials. Open the exact isolated target profile and let the person sign in directly. Credentials must not enter chat, command flags, standard input, environment variables, protocol payloads, screenshots, recordings, or evidence.

Studio owns setup: it provisions one opaque profile binding for the exact project, target, environment, and origin, opens that profile at the exact origin, proposes bounded non-secret route-and-accessible-role markers, and asks the person to confirm one. Never enter a free-form marker, expose a profile path, reuse a profile for another target, or substitute the ordinary agent browser session. The concrete Playwright adapter keeps browser state below the ignored local-store root. If Playwright or its configured headed browser cannot launch, report the capability gap and stop; never bypass authentication.

Studio is also the sole long-lived owner of that persistent context. Register `browser.user-session` contract version `1.0` and `browser.control` with the same adapter identity. Authenticated CLI agent commands delegate to Studio's private local broker and fail closed when it is unavailable. Use the opaque `usersession_…` lease target for every browser action and evidence capture; never run the lease in a generic browser. Closing Studio disposes every owned context.

For a workflow-declared route, inspect the current revision, then bind before requesting any lease. `agent.route.bind` only binds an active run owned by this host before any lease. Its payload contains only the workflow-declared route ID, typed parameters, and readiness name; never a path or URL. The result returns the binding ID, not a derived path or marker. Propose `navigate` with only the opaque `run-route:binding_…` target and `observe`, issue the screenshot slot, execute once through `workflow browser execute`, then register and commit the evidence. Route declarations are a generic Workflows capability; each route template is application-owned. An attempted navigation is never replayed; inspect and reconcile after failure.

For this authenticated path, execute and capture through `workflow browser execute --file PATH --json`, not the generic Chrome procedure. After an allowed proposal, issue the step screenshot slot and pass exactly `runId`, `hostId`, `leaseId`, `slotId`, and the latest `expectedRevision`. The owner derives the approved actions and captures untouched bytes in the same session. Supported actions are observe, navigate to `declared-start-url`, and exact targets `role:button:NAME`, `role:link:NAME`, `role:radio:NAME`, or `role:menuitem:NAME`. Bounded synthetic text uses `enter-text`, an exact `role:textbox:NAME` or `role:searchbox:NAME` target, and workflow-pinned `textInput: {kind: synthetic, value: dogfood-example}`. Values are at most 120 characters, start with `dogfood-`, and contain only ASCII letters, digits, spaces, or hyphens; the empty value clears the field. Only ordinary text/search inputs and textareas without credential-like hints or autofill purposes are eligible. Arbitrary literals, credential fields, selectors, and filesystem paths remain unavailable. Register the returned slot and assess/commit normally. Never repeat an attempted lease; inspect and reconcile uncertainty. Session setup and capture capability must be verified before advertising them; never substitute a generic browser or stage screenshots from another session.

An authenticated `upload-file` action uses only an exact `label:NAME` target and workflow-pinned `inputRef: {kind: synthetic-file, name: INPUT_NAME, filename: dogfood-NAME.csv, sizeBytes: N, mimeType: text/csv, sha256: sha256:HEX}` plus the `file-upload` capability. While that action lease is active, create a `browser.upload-stage/v1` request with exactly these top-level fields: `schema`, `runId`, `hostId`, `leaseId`, `stepId`, `expectedRevision`, `inputName`, `filename`, `sizeBytes`, `mimeType`, `sha256`, and `contentBase64`. Copy `inputRef.name` to `inputName`; do not include `inputRef`, `target`, `kind`, `capability`, a selector, or a source path. For example: `{ "schema": "browser.upload-stage/v1", "runId": "run_...", "hostId": "host_...", "leaseId": "lease_...", "stepId": "upload-guests", "expectedRevision": 7, "inputName": "guest-import", "filename": "dogfood-guests.csv", "sizeBytes": 42, "mimeType": "text/csv", "sha256": "sha256:...", "contentBase64": "..." }`. Pass the request file to `workflow browser stage-upload --file PATH --json`. The runner accepts only a bounded UTF-8 synthetic CSV, binds it durably to that lease and staging revision, and exposes no source path. Valid same-lease heartbeats and replacement runner-issued screenshot slots may advance the current revision without invalidating that binding. `workflow browser execute` reopens and rehashes only that staged artifact, verifies the approved labeled control is a single file input, uploads the in-memory bytes through the same opaque session/tab, and consumes the artifact after execution, uncertainty, cancellation, expiry, or reconciliation. Never use a generic upload API or supply a selector, host file path, profile path, or replacement session.

When the workflow is on another same-origin route, the owner verifies the confirmed marker in a temporary page inside the same authenticated context, then closes that page without moving the workflow page. A missing marker or expired session still fails verification.

Verify the confirmed non-secret marker before requesting the first action lease and after any authentication challenge. The runner performs its own marker verification before every run and immediately before a governed consequential action. Profile existence and an earlier successful verification are never readiness proof. If authentication is lost without an uncertain action, pause in `awaiting-authentication`, use Studio's reauthentication control to open the same profile, let the person sign in, and send `agent.authentication.verify` for the same run and owning host before resuming.

If an action result is uncertain, reconcile it before authentication recovery and never repeat the action: `completed` records the classification without advancing the workflow step; training remains paused. Only `not-executed` returns to marker verification. If continuation is unavailable, safely stop and start a fresh run. Clearing must remove the browser profile before the local binding; when browser cleanup fails, retain `clear-failed` and offer retry instead of claiming success.

An execution error can coexist with an active lease: the durable attempt receipt prevents replay before the lease expires. Do not heartbeat or repeat an uncertain attempt. Use `run emergency-stop` with the current revision and active lease, then inspect and reconcile; otherwise inspect after expiry to trigger lease recovery. A `preparation` diagnostic alone is not proof of nonexecution after a crash. For a completed execution interrupted before commit, retrieve its existing screenshot slot and register the staged evidence before committing while the lease remains valid. Preserve uncertain attempts and check owned fixture cleanup before a fresh run.
